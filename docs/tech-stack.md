# 技术选型文档

## 1. 使用规模与部署前提

第一版面向小范围自用，主要用户是项目作者和对象，最多扩展到约 10 人。系统优先考虑开发效率、部署简单、数据可控和后续可扩展，不按公开 SaaS 的高并发、多租户复杂度或计费额度系统设计。

部署方式采用单机 Docker Compose，运行在已有服务器上。前端、后端、数据库和本地文件目录都由同一台服务器承载。

## 2. 总体选型

- 前端：React + Vite + TypeScript。
- 前端 UI 与状态：Tailwind CSS、shadcn/ui、Radix UI、lucide-react、React Router、TanStack Query、react-hook-form、Zod。
- 后端：FastAPI + Python。
- 数据库：PostgreSQL。
- 文件存储：服务器本地文件目录，通过 Docker volume 挂载。
- AI 能力：OpenAI API。
- 素材生成与管理：Rough.js 生成统一手绘质感 SVG，人工审核少量免费外部素材。
- 认证方式：账号密码。
- PNG 导出：前端浏览器导出。
- 部署：Docker Compose + Nginx 或 Caddy 反向代理 HTTPS。

## 3. 前端

前端使用 React、Vite 和 TypeScript，并基于成熟组件库搭建界面。

选择原因：

- 手帐画布、轻量编辑、历史列表和生成状态都需要较强交互，React 更合适。
- Vite 启动和构建速度快，适合小型单页应用。
- TypeScript 能约束结构化手帐 JSON，降低前后端字段不一致的风险。
- shadcn/ui 基于 Radix UI 和 Tailwind CSS，组件源码可放进项目内维护，适合小型自用项目长期控制。
- Radix UI 提供弹窗、菜单、Tabs、Select 等无样式基础交互，减少自行处理键盘和可访问性细节。
- lucide-react 用作界面图标，不作为手帐内容素材，避免 UI 图标感进入手帐画面。
- TanStack Query 负责接口请求缓存、加载状态和错误状态。
- react-hook-form 和 Zod 负责表单状态与输入校验。
- React Router 负责登录、创建、历史、详情和素材预览页面路由。

前端主要职责：

- 登录和注册入口。
- 图片上传与缩略图预览。
- 描述、日期、地点、心情标签输入。
- 手帐预览画布渲染。
- 标题、正文、模板和装饰元素的轻量编辑。
- 素材库预览页。
- 调用后端生成、保存、读取历史手帐。
- 使用浏览器能力导出 PNG。

前端组件原则：

- 常规按钮、输入框、弹窗、Tabs、Select、Toast、Tooltip、卡片和表单控件优先使用 shadcn/ui。
- 图标按钮优先使用 lucide-react。
- 页面级视觉风格由 Tailwind CSS 和项目 CSS 变量控制，不直接依赖大而全的商业模板。
- 画布渲染、照片拼贴、素材摆放和 PNG 导出属于业务核心，使用项目内自定义组件实现。

## 4. 后端

后端使用 FastAPI 和 Python。

选择原因：

- AI 调用、图片处理、结构化 JSON 校验和后续异步任务更适合 Python 生态。
- FastAPI 对类型、接口文档和 JSON API 支持较好。
- 对 2-10 人规模，单个后端服务足够。

后端主要职责：

- 用户注册、登录和会话管理。
- 图片上传、校验、保存和访问控制。
- 调用 OpenAI API 生成手帐结构化数据。
- 管理内置素材库，并为后续少量定制装饰元素生成预留接口。
- 保存和读取手帐历史。
- 提供前端所需的 REST API。

## 5. 数据库

数据库使用 PostgreSQL。

选择原因：

- 支持多用户、历史记录、JSON 字段和后续查询扩展。
- 比 SQLite 更适合长期保存账号、手帐和图片元数据。
- 单机 Docker 部署成本低，维护复杂度可接受。

核心数据包括：

- 用户。
- 上传图片元数据。
- 手帐记录。
- 手帐结构化 JSON。
- 装饰素材元数据。

## 6. 文件存储

第一版使用服务器本地文件目录保存上传图片、缩略图、生成素材和导出缓存，通过 Docker volume 挂载持久化。

选择原因：

- 用户规模小，本地文件足够。
- 不需要额外部署 MinIO 或接入对象存储。
- 备份方式直接，可随数据库一起做服务器级备份。

约束：

- 文件路径不能直接暴露为无鉴权公开路径。
- 后端需要控制当前用户只能访问自己的图片和手帐资源。
- 原图长期保存。
- 上传后生成缩略图。
- 删除手帐时同步删除关联原图和缩略图。
- 后续如迁移到 S3、R2 或 MinIO，应尽量只替换文件存储适配层。

## 7. AI 能力

第一版接入 OpenAI API。

使用方式：

- 第一版真实调用 OpenAI API，不使用纯 mock 生成作为正式流程。
- 文案、主题、布局建议和结构化手帐 JSON 由文本/多模态模型生成。
- AI 必须接收并理解用户上传图片内容。生成链路不能只传图片 ID、尺寸或缩略图元数据；需要把图片以模型可读取的形式传入，例如鉴权后的临时图片 URL 或后端编码后的图片内容。
- 默认模型配置为 `gpt-5.5`，优先保证文案质感、主题理解和排版 JSON 稳定性；如果第三方 OpenAI 兼容服务使用不同模型名，可以通过 `OPENAI_MODEL` 覆盖。
- 支持通过 `OPENAI_BASE_URL` 配置第三方 OpenAI 兼容服务。当前实现使用 Responses API，如果第三方服务不支持 `/v1/responses`，需要再增加 Chat Completions 兼容模式。
- 第一阶段装饰元素从内置素材库中选择。
- 后续可以接入图像生成模型生成少量定制装饰元素，但不作为第一阶段硬依赖。

后端需要对 AI 输出做结构校验，不能直接信任模型返回。生成失败、图片读取失败或结构不合法时，需要给用户可理解的失败提示，并允许重新生成。

## 8. 认证与访问控制

第一版采用账号密码登录。

要求：

- 用户登录后才能上传图片、生成手帐、保存历史和导出。
- 用户只能访问自己的图片和手帐。

选择原因：

- 不依赖邮件服务。
- 对 2-10 人自用场景足够简单。
- 后续需要限制注册时，可以增加邀请码或白名单。

## 9. 素材库

第一版使用免费内置素材库，优先使用 Rough.js 和项目模板生成统一风格 SVG，外部免费素材只作为人工审核后的补充。

要求：

- 素材文件随项目版本管理。
- 每个素材有结构化元数据。
- 元数据包含分类、标签、授权、来源和质量状态。
- 只有 approved 素材可以参与 AI 自动选择。
- 网站提供素材库预览页，方便人工检查素材质量。
- 免费不等于可随意使用。即使项目不做商业用途，也只引入授权清晰、来源可追溯、质量通过预览页检查的素材。

素材库预览页由前端实现，素材元数据由后端或静态 JSON 提供。第一版不要求在网页内编辑素材。

## 10. PNG 导出

第一版采用前端浏览器导出 PNG。

实现方向：

- 前端将结构化手帐 JSON 渲染为固定尺寸画布区域。
- 第一版固定画布和导出尺寸为 1080 x 1440。
- 使用 `html-to-image`、`dom-to-image` 或同类库导出 PNG。
- 导出结果应与预览画布一致。

约束：

- 图片资源需要避免跨域导致导出失败。
- 字体、图片和装饰元素加载完成后才能导出。
- 如果后续发现浏览器导出稳定性不足，再升级为后端 Playwright/Chromium 截图导出。

## 11. 部署

第一版使用 Docker Compose。

建议服务：

- `frontend`：构建并提供前端静态资源，或由反代服务托管静态文件。
- `backend`：FastAPI 服务。
- `postgres`：PostgreSQL 数据库。
- `proxy`：Nginx 或 Caddy，负责 HTTPS、反向代理和静态资源访问。

持久化数据：

- PostgreSQL 数据目录。
- 上传图片和生成文件目录。
- 后端运行所需配置。

敏感信息通过环境变量配置，不提交到 Git。

## 12. 暂不采用的方案

### 12.1 Next.js 全栈

Next.js 可以减少项目数量，但本项目后端会涉及 AI 编排、图片处理和后续异步任务，Python 更自然。

### 12.2 Django 一体化

Django 的账号和后台能力成熟，但手帐画布和轻量编辑对前端交互要求更高，纯模板或少量 React 组件会增加前端体验成本。

### 12.3 MinIO 或云对象存储

第一版用户规模很小，本地文件目录足够。引入 MinIO 或云对象存储会增加部署和运维复杂度。

## 13. 后续可扩展方向

- 后端异步任务队列，用于较慢的 AI 生成、图片处理和批量导出。
- 后端 PNG/PDF 导出。
- 对象存储适配层，迁移到 MinIO、S3 或 R2。
- 邀请码、白名单和用户管理后台。
- 模板和素材管理后台。
- 更严格的生成额度和成本统计。
