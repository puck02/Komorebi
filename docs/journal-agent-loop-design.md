# 手帐视觉 Agent Loop 设计

## 1. 目标

在现有 AI 手帐生成能力上增加视觉复审闭环。系统生成初稿后不立即展示，而是先渲染真实手帐画面，由视觉模型检查图片与文字匹配、素材位置、遮挡、排版节奏和整体美观度。不满足质量要求时自动修订，最多调整 3 轮。

单个任务最多包含：

- 1 次初稿生成。
- 3 次复审后的修订。
- 4 个布局版本。

达到调整上限仍未通过时，展示全部版本中评分最高的一版，不机械地使用最后一版。

## 2. 设计原则

- 用户前端不展示半成品，只展示生成阶段。
- 用户上传或拖拽后的图片顺序始终固定。
- 程序规则检查优先于模型主观评分。
- 复审模型只提出明确问题和修订指令，不直接绕过后端规则。
- 每轮修改后继续执行现有清洗逻辑，避免修订引入新问题。
- 第一版面向最多 10 个用户，不引入 Redis、Celery 或独立队列服务。

## 3. 模型配置

初稿生成与修订使用：

```env
OPENAI_MODEL=gpt-5.5
```

视觉评审使用：

```env
OPENAI_REVIEW_MODEL=gpt-5.4-mini
```

两个模型共用现有 `OPENAI_BASE_URL` 和 `OPENAI_API_KEY`。第三方渠道必须支持 `gpt-5.4-mini` 的图片输入能力。

## 4. Agent Loop

每个后台生成任务按以下步骤执行：

1. 使用 `gpt-5.5` 读取用户描述和按顺序排列的图片，生成初稿 JSON。
2. 后端执行规则清洗：
   - 校验图片 ID。
   - 固定用户图片顺序。
   - 修复非法素材。
   - 控制装饰密度。
   - 阻止文字遮挡图片。
   - 将胶带吸附到照片边缘。
3. 使用 Playwright 打开内部渲染页，按照真实前端视觉渲染当前 JSON，并生成压缩截图。
4. 使用 `gpt-5.4-mini` 评审：
   - 当前手帐截图。
   - 用户图片展示图，按用户排序编号。
   - 用户原始描述。
   - 当前结构化 JSON。
5. 评审模型返回严格 JSON：
   - `score`：总分。
   - `passed`：视觉模型是否满意。
   - `scores`：分项评分。
   - `issues`：问题列表，每项包含类型、严重程度、关联图片或素材 ID、修改建议。
   - `summary`：交给修订模型的简短指令。
6. 如果程序规则检查通过，视觉评分达到 `85/100`，并且不存在硬失败问题，则结束。
7. 否则，把评审结果、当前 JSON、原始图片和描述交给 `gpt-5.5`，生成修订版完整 JSON。
8. 重复规则清洗、截图和评审，最多调整 3 轮。
9. 持续记录评分最高的布局版本。达到上限时保存最佳版本。

每轮只修复评审指出的具体问题，不鼓励模型推翻整版重做。

## 5. 评分规则

视觉评分总分为 `100`：

| 项目 | 分值 | 检查重点 |
| --- | ---: | --- |
| `layout` | 25 | 布局节奏、留白、画布长度、视觉平衡 |
| `photoTextMatch` | 25 | 正文和 caption 是否对应正确照片 |
| `decorationPlacement` | 20 | 胶带、贴纸、底纸和纹理的位置是否正确 |
| `readability` | 20 | 文字是否清晰可读，是否发生遮挡 |
| `coherence` | 10 | 主题、配色、素材风格是否统一 |

视觉评审需要检查手帐是否有明确视觉焦点：主图或主视觉区域是否突出，章节之间是否有主次关系，留白是否形成节奏，而不是把照片和文字平均铺开。

视觉评审需要检查章节图文匹配：`content.sections[].body` 必须只描述对应 `imageIds` 中的照片，不能把其他章节或其他图片的内容写进来。

视觉评审需要检查装饰是否有功能：胶带应像固定照片或便签，底纸应承载文字或建立层次，贴纸应呼应主题或填补留白，不能随意漂浮、遮挡主体或只是堆数量。

视觉评审需要判断成品是否像精致电子手账，而不是普通图文列表。合格结果应有拼贴层次、手写日记感、照片与文字之间的明确关系。

视觉评审需要同时检查素材丰富度：装饰数量是否过少、`assetId` 是否重复过多、外部 approved 素材是否几乎没有被使用。素材丰富度不足不等同于布局硬失败，但会作为中等严重度问题进入修订轮。

以下情况属于硬失败，即使总分达到阈值也不能结束：

- 图片缺失、重复或顺序变化。
- 文字与图片矩形重叠。
- 贴纸覆盖照片主体安全区。
- 胶带没有贴近照片边缘。
- 素材超出画布。
- 使用未审核素材或不存在的素材 ID。
- 装饰超过密度上限。
- 正文或 caption 与照片内容明显不匹配。

## 6. Prompt 设计

Agent Loop 拆分为三个角色，不使用一个万能 Prompt。三个角色共享不可违反的规则，但职责和输出结构不同。视觉评审器只负责指出问题，不能直接绕过规则修改布局。

### 6.1 初稿生成器

模型：`gpt-5.5`

输入：

- 用户描述。
- 按用户确认顺序编号的图片。
- `approved` 素材列表。
- 手帐 JSON schema。
- 不可违反的布局规则。

目标：

- 理解图片实际可见内容。
- 为每张图片输出结构化 `imageUnderstanding`，包含 `imageId`、`summary`、`scene`、`subjects`、`mood`。
- 按图片顺序组织叙事和分组。
- 只允许把相邻图片合并为同一章节，每章绑定 1-3 张图片。
- 生成自然、简短的日记文案。
- 输出完整初稿 JSON。

核心 Prompt：

```text
你是日记手帐设计师。图片数组顺序是用户上传或拖拽排序后的叙事顺序，禁止重排。
必须先逐张理解图片，在 content.imageUnderstanding 中覆盖全部图片，顺序和图片 order 一致。
imageUnderstanding.summary 只能描述对应 imageId 的真实可见内容，不要使用用户描述替代视觉理解。
请把相邻图片按内容分成 2-5 个章节，禁止把不相邻图片放入同一章节。
content.sections 每章绑定 1-3 张图片，每章 body 写 30-80 字自然日记。
正文要像用户当天随手写下的日记，不要写成 AI 总结，不使用空泛套话。
caption 必须描述对应 imageId 的真实可见内容。
装饰素材只能使用 approved assetId。
胶带用于固定照片边缘；贴纸不得遮挡照片主体；底纸不得压住照片内容。
输出严格 JSON，不要输出解释。
```

### 6.2 视觉评审器

模型：`gpt-5.4-mini`

输入：

- 用户描述。
- 按顺序编号的原图展示图。
- 当前手帐渲染截图。
- 当前手帐 JSON。
- 程序规则检查结果。
- 评分 schema。

目标：

- 只做质量审核，不修改布局 JSON。
- 识别截图中真实存在的问题。
- 对照原图检查正文和 caption。
- 输出结构化评分和修订建议。

输出 schema：

```json
{
  "score": 78,
  "passed": false,
  "scores": {
    "layout": 19,
    "photoTextMatch": 20,
    "decorationPlacement": 13,
    "readability": 17,
    "coherence": 9
  },
  "issues": [
    {
      "type": "decorationPlacement",
      "severity": "high",
      "targetIds": ["sticker_camera_07", "img_2"],
      "description": "贴纸覆盖了第二张照片的主体区域",
      "instruction": "将 sticker_camera_07 移到 img_2 右下方空白处"
    }
  ],
  "summary": "保留当前整体布局，只移动遮挡主体的贴纸，并增加第二组图片与正文之间的留白。"
}
```

视觉评审 Prompt 必须明确：

- 不因个人审美随意扣分。
- 每个问题必须能从截图、原图或规则检查结果中找到证据。
- `passed=true` 必须满足总分 `>=85`，并且不存在硬失败。
- 图文匹配必须对照原图编号，不允许凭空推测。
- 必须检查视觉焦点、主次关系、留白节奏和是否像电子手账。
- 必须检查章节正文是否对应章节图片，不能只看全篇 summary。
- 必须检查装饰是否有功能，而不是只看数量。
- 每轮优先指出最影响体验的 `3-6` 个问题，避免修订范围过大。

### 6.3 定向修订器

模型：`gpt-5.5`

输入：

- 当前最佳版本 JSON。
- 用户描述。
- 按顺序编号的原图展示图。
- 当前最佳版本截图。
- 视觉评审 JSON。
- `approved` 素材列表。
- 不可违反的布局规则。
- 当前轮次和历史最佳分数。

目标：

- 只修复评审指出的问题。
- 返回完整新版 JSON。
- 保留已经正确的内容和布局。
- 避免无关重写和整版推翻。

核心 Prompt：

```text
你是手帐排版修订师。根据视觉评审问题修订当前 JSON。
只修改解决 issues 所必需的字段，保留已经合理的设计。
禁止修改图片集合和图片顺序。
正文或 caption 只有在评审指出图文不匹配时才修改。
不得新增列表之外的 assetId。
只处理视觉评审 issues 中列出的 3-6 个主要问题。
不要改变未被点名的问题区域；如果 issues 没有要求重做整体版式，不要推翻整版布局。
输出完整 JSON，不要输出解释。
```

每轮附加上下文：

```text
这是第 2/3 轮修订。
上一轮得分：78。
当前最佳得分：84。
不得扩大修改范围。若评审建议互相冲突，优先处理 high severity 问题。优先做局部移动、缩放、换素材或微调文字。
```

### 6.4 程序约束优先

Prompt 不能替代代码检查。每轮模型输出后，后端继续强制：

- 恢复图片集合和图片顺序。
- 删除或替换非法素材。
- 修正胶带位置。
- 去掉遮挡主体的贴纸。
- 调整文字块，避免与图片重叠。
- 限制装饰数量。
- 检查装饰数量下限、重复素材和外部素材使用比例。
- 修复画布高度。

### 6.5 防止循环退化

- 每轮基于当前评分最高版本修订，不基于较差版本继续修改。
- 如果新版评分下降，保留历史最佳版。
- 每轮只处理评审器列出的 `3-6` 个主要问题。
- 高严重程度问题优先于低严重程度问题。
- 到达 3 轮上限时，无论最后一版评分如何，都保存历史最佳版。

## 7. 修订边界

每轮允许修改：

- 标题、正文段落、caption。
- 图片尺寸、位置和轻微旋转。
- 素材选择、位置、尺寸和旋转。
- 画布高度、配色和主题。

始终禁止修改：

- 用户图片集合。
- 用户拖拽后的图片顺序。
- 只使用 `approved` 素材的约束。
- 文字不得遮挡图片、贴纸不得遮挡主体等基本保护规则。

## 8. 后台任务

当前同步生成接口改为后台任务：

```text
POST /api/journal-generation-jobs
GET  /api/journal-generation-jobs/{job_id}
```

前端流程：

1. 用户提交图片和描述。
2. 后端立即返回 `jobId`。
3. 前端跳转到 `/generation/:jobId`。
4. 页面每 2 秒轮询任务状态。
5. 完成后自动跳转到手帐详情页。
6. 失败时显示错误，并允许返回创建页重新生成。

页面只展示简洁阶段：

- `正在理解照片`
- `正在生成初稿`
- `正在检查排版`
- `正在调整细节 · 第 2/3 轮`
- `正在保存手帐`

任务表至少包含：

| 字段 | 用途 |
| --- | --- |
| `id` | 任务 ID |
| `user_id` | 所属用户 |
| `status` | `queued`、`running`、`completed`、`failed` |
| `stage` | 当前用户可见阶段 |
| `revision_round` | 已执行修订轮数 |
| `max_revision_rounds` | 最大修订轮数，默认 `3` |
| `best_score` | 当前最佳视觉评分 |
| `journal_id` | 完成后生成的手帐 ID |
| `error_message` | 失败原因 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

第一版使用后端进程内线程池执行任务，状态落到数据库。单个任务串行执行，最多同时处理 `2` 个任务。服务重启时，将未完成任务标记为失败，用户可重新生成。

## 9. 内部渲染

新增 Playwright + Chromium 截图链路：

- 后端启动无头 Chromium。
- 打开仅用于截图的内部渲染页。
- 内部渲染页复用用户详情页的 `JournalCanvas` 组件和 CSS。
- Chromium 通过仅绑定本机的内部地址打开渲染页。
- 草稿 JSON、图片展示图和素材接口必须携带一次性短时随机 token；token 仅供当前截图任务使用，任务结束或超时后立即失效。
- 等待字体、图片和素材加载完成后截图。
- 对截图做压缩，控制传给评审模型的大小。
- 单任务内复用浏览器实例，任务结束后关闭，避免资源泄漏。

截图失败时，本轮记为失败。已有可用候选则保存最佳版本，否则任务失败。

## 10. 后端组件

新增或调整以下组件：

| 组件 | 责任 |
| --- | --- |
| `generation_jobs.py` | 创建任务、查询状态、处理失败恢复 |
| `journal_agent.py` | 驱动初稿、规则检查、截图、评审、修订闭环 |
| `journal_renderer.py` | Playwright 浏览器生命周期和截图 |
| `openai_client.py` | 初稿、视觉评审和修订请求 |
| 数据库迁移 | 新增生成任务表 |

现有 `journal_generator.py` 继续负责确定性清洗和保护规则。模型不能绕过它。

## 11. 前端组件

新增：

- `/generation/:jobId` 页面。
- 任务状态轮询 API。
- 内部手帐渲染页。

调整：

- 创建页提交后跳转生成状态页，不再等待同步生成完成。
- 完成后自动跳转详情页。

## 12. 错误处理

- 初稿生成失败：任务失败，不创建手帐。
- 评审模型失败：记录本轮错误；已有可用候选则保存最佳版本，否则任务失败。
- 修订模型失败：记录本轮错误；已有可用候选则保存最佳版本。
- 修订 JSON 无效：丢弃该版本，保留已有最佳版本。
- Playwright 截图失败：记录本轮错误；已有可用候选则保存最佳版本。
- 达到 3 轮仍未通过：保存最佳版本，任务状态仍为 `completed`。
- 用户只能读取自己的生成任务。

## 13. 日志与隐私

日志记录：

- `job_id`
- 阶段
- 修订轮次
- 规则检查结果
- 视觉评分
- 最佳版本轮次
- 错误类型
- 每轮画布高度、图片数、文本框数、装饰总数、唯一素材数、外部素材数。
- 每轮使用的素材 ID 列表，最多记录前 30 个。

日志不记录：

- 图片 Base64。
- API Key。
- 完整用户隐私文本。
- 完整模型输入。

后端输出 JSON 行日志，logger 名称为 `komorebi.agent`。在当前 systemd 用户服务部署中，可以用以下命令查看：

```bash
journalctl --user -u komorebi-backend.service -f
journalctl --user -u komorebi-backend.service -f | rg '"event":"agent\.'
journalctl --user -u komorebi-backend.service --since "30 minutes ago" | rg '<job_id>'
```

关键事件：

- `agent.job_started`：任务开始，包含图片数、可用素材数、描述长度。
- `agent.progress`：阶段推进，包含 `stage`、`revision_round`、`score`、`best_score`。
- `agent.candidate_reviewed`：每轮候选版评审结果，包含视觉分、规则问题、评审问题和素材使用摘要。
- `agent.revision_requested`：准备进入下一轮修订。
- `agent.job_completed`：任务完成，包含最终手帐 ID、分数、轮次和是否通过阈值。
- `agent.job_failed`：任务失败，包含错误类型和错误信息。

## 14. 测试范围

单元测试：

- 达到阈值提前停止。
- 规则硬失败时继续修订。
- 最多修订 3 次。
- 达到上限后保存最佳版本。
- 修订后图片集合和顺序不变。
- 非法素材继续经过规则清洗。

客户端 mock 测试：

- 评审请求包含截图、原始图片、描述和当前 JSON。
- 评审 JSON 正确解析。
- 修订请求包含评审问题和当前 JSON。
- `OPENAI_REVIEW_MODEL` 默认值为 `gpt-5.4-mini`。

Playwright 冒烟测试：

- 内部渲染截图非空。
- 动态画布高度正确。
- 图片、素材和白路俏丽手写体加载完成后再截图。

API 测试：

- 创建生成任务。
- 查询任务进度。
- 任务完成后返回手帐 ID。
- 失败状态返回明确错误。
- 用户不能读取其他用户的任务。

## 15. 非目标

第一版不做：

- Redis、Celery 或独立任务队列。
- 多进程任务协调。
- 用户界面显示内部评分。
- 用户查看中间版本。
- 用户手动恢复服务重启前的未完成任务。
- 并发超过 `2` 个生成任务。
